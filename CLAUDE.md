# Contexto do projeto: plataforma de sites estáticos de carros

Responda em português informal. Dono do projeto: Wellington (dev PHP/Yii, trabalha no CRM Revenda Mais).

## Objetivo
Plataforma com ~2500 sites estáticos de revendas de carros, cada um em um domínio próprio. Os sites têm busca, filtros e links personalizados. As atualizações precisam ser muito práticas, porque são muitos sites.

## Decisões de arquitetura (já tomadas)
1. **Um site por domínio, um estoque por site:** `sites-config/<dominio>/` tem `site.json` (template, tema, textos, filtros, restrições, motor, vendedores, fotosBase, url e as `lojas` do site), `web/` (espelho do site: home, multipla e páginas), `estoque.json` (o ÚNICO JSON de carros do site; cada carro diz sua `loja`, opcional se o site tem uma loja só) e `assets/` (logo, banner...). O nome da pasta é o domínio e o id do site (não há campo `id`). Não existe mais estoque nem loja compartilhados entre sites (decisão do Wellington: "sempre será passado só um json de estoque de carros").
2. **Core isolado, visual separado:**
   - `core/` é só código: `motor/<versao>/engine.js` (busca, filtros em cascata, estado na URL e WhatsApp; não mexe em DOM, roda no navegador e no Node), `ui/` (liga o motor à página), `caminhos.js` (todos os caminhos), `build.js`, `cli.js`, `atualizar.js`, `sites.js` (validar/gravar cadastro), `fotos.js`.
   - `api/` é a porta de entrada HTTP (portas e adaptadores): só traduz HTTP ↔ core. **`core/` nunca importa de `api/`** (um teste cobra).
   - `templates/<nome>/` é autocontido: `template.json`, `paginas/` com UM ARQUIVO POR TIPO DE PÁGINA (decisão do Wellington): `home.html` (página principal), `multipla.html` (listagem do estoque; era `index.html`), `carro.html`, `vendido.html` e `pagina.html` (moldura das páginas de conteúdo e da 404); mais `blocos/`, `parciais/`, `paginas-padrao/`, `css/`, `js/`, `img/`. Hoje há `barra-topo`, `lateral`, `trokey` e `template-basico` (era `servopa`, renomeado em 2026-11-08). Não existe base compartilhada entre templates.
   - **`sites-config/<dominio>/web/` = espelho do site público** (decisão do Wellington, 2026-11-08): `web/index.json` → `/` (home), `web/multipla.json` → `/multipla/` (`blocosAntes`/`blocosDepois`; arquivo vazio = sem configuração; era `"estoque"` no site.json, que agora é recusado; API `GET/PUT/DELETE /v1/sites/<d>/multipla`; todo template precisa de `{{{blocosAntes}}}`/`{{{blocosDepois}}}` no multipla.html, um teste cobra), `web/paginas/` → `/paginas/<nome>/`. Pasta antiga `sites-config/<d>/paginas/` e home em `web/paginas/index.json` = erro claro; `ferramentas/mover-paginas.js` migra. Caminhos: `C.web`, `C.home`, `C.multipla`, `C.paginasLivresSite`; lista de páginas de blocos: `PL.paginasJsonDoSite`.
   - Páginas de conteúdo (home institucional, vender, lojas, política) são **arquivos em `sites-config/<dominio>/web/paginas/`** (decisão do Wellington: toda página que não é padrão fica ali; é onde o web designer cria páginas; o `site.json` NÃO tem lista de páginas e o build recusa `"paginas"` nele; `ferramentas/mover-paginas.js` migra). `web/index.json` = home, `web/paginas/lojas.json`, `a/b.json` (páginas de blocos) ou `.html` livre. **Endereço público: `/paginas/<nome>/`** (decisão do Wellington; constante `PASTA_PAGINAS`), inclusive as páginas padrão (`/paginas/lgpd/`); só a home fica na raiz. O build ajusta links simples (`"contato/"`, `href="/lojas/"`) para `/paginas/` (`paraPagina`). **O build NUNCA gera nada de página fora de `/paginas/`** (decisão do Wellington: a raiz do site tem só home, `multipla/`, `carros/`, `paginas/` e arquivos); endereço antigo de página (`/contato`, de antes da mudança ou do site do Revenda Mais) é 301 da hospedagem (`infra/cloudfront/roteador.js`: tudo sem extensão fora de `PASTAS_DO_SITE` → `/paginas/...`); redirecionamentos HTML antigos na raiz (`paginasMovidas` de estados velhos) são apagados pelo build; cada tipo de bloco é `templates/<nome>/blocos/<tipo>.html`, a moldura é `paginas/pagina.html`, e pedaços comuns ficam em `parciais/` (`{{> nome}}`). `cabecalho` e `rodape` também vêm do `site.json`.
   - **A listagem do estoque fica SEMPRE em `/multipla/`** (constante `CAMINHO_ESTOQUE` no build); a raiz é a home institucional (`sites-config/<dominio>/web/index.json`, ou a `HOME_PADRAO` do core: banner + vitrine). Todo template precisa dos 5 arquivos de `paginas/` (o build recusa com "falta paginas/x.html") e dos blocos `banner`, `vitrine`, `titulo`, `texto`, `formulario` e `lojas`. O bloco `listagem` (template-basico) ou o bloco `componente` estoque põem o estoque interativo dentro de uma página.
   - **Compatível com o Revenda Mais (migração sem perder SEO):** campo `link` no carro (o link que o Revenda Mais já usa; tem regras/bugs próprios como cidade sem a letra acentuada "Maring", "//" e "R/t", impossíveis de recalcular). Endereços com espaço/acento vão codificados (função `url()` no build). Sitemap real da Servopa: só home, /multipla, /financiamento, /avaliacao, /contato, /multipla/marca/* e os carros.
   - **Rotas da listagem** (decisão do Wellington, 2026-11-08): os filtros ficam no CAMINHO depois de `/multipla/`, em pares `nome/valor`, em qualquer ordem, com `|` para vários valores (`/multipla/revenda-estado-cod/PR|RS/revenda-cidade-nome/Canoas|Cascavel/marca/AUDI|BMW/veic-anomodelo/2027`; nomes do Revenda Mais com `-` no lugar de `_` e valores SEMPRE minúsculos (`marca/audi|bmw`), decisões do Wellington: `NOMES` em `core/ui/rotas.js`; lê também com `_` e os nomes do motor; busca, ordem e vendedor continuam na query: `?q=&ord=&v=`). O site continua ESTÁTICO: o build NÃO gera arquivo depois de `/multipla/` (só `multipla/index.html`); a hospedagem entrega o mesmo `multipla/index.html` para qualquer `/multipla/...` (rewrite 200 em `infra/cloudfront/roteador.js`; local: `node ferramentas/servidor-local.js 8080`, que usa a mesma função; o `python -m http.server` não serve). Regra única em `core/ui/rotas.js` (UMD: navegador, build e testes): `ler` aceita os nomes do Revenda Mais (`revenda_estado_cod`, `revenda_cidade_nome`, `modelo-marca`...), `montar` escreve na ordem dos filtros do site (mesmo filtro = mesmo endereço). A `ui-lista` lê a rota (+ query antiga `?marca=`), reescreve a URL e o canonical, acerta maiúscula/acento (`toyota` → "Toyota", prefixo único "Maring" → "Maringá"); o build põe no `<head>` da multipla um script que cria `<base href=".../multipla/">` em rota funda (css/js/estoque.json relativos continuam certos). Links de filtro do build (`{{estoque.marcas}}`, lojas...) e os escritos à mão (`paraFiltro`: `"multipla/?carroceria=Moto"`, `"multipla/revenda_cidade_nome/X"`) saem como rota canônica. **Motor v3** = vários valores por filtro (OU), cascata respeitada (cidade de outro estado sai), ano EXATO por padrão (lista do mais novo ao mais velho; `{ "campo": "ano", "tipo": "minimo" }` volta ao "a partir de"); valor do LINK que não existe no estoque fica no filtro e dá "Nenhum carro encontrado" (decisão do Wellington); pela tela (`definir`) só vale o que existe, e trocar um filtro limpa só os que dependem dele; v1/v2 aceitam um valor só. `paginasFiltro`/`formatoUrls` não existem mais (só aviso).
   - **Ordem de exibição vem do estoque:** campo `ordem` (ou a posição no arquivo) → o `estoque.json` gerado (sites-public) sai nessa ordem (campo `r`) e o motor v2 tem a ordenação `destaque` (padrão). Campos opcionais do carro: `ordem`, `destaque`, `carroceria`.
   - **Páginas padrão** (`templates/<nome>/paginas-padrao/*.json`: contato, financiamento, avaliação, política de privacidade, cookies, LGPD; decisão do Wellington: NÃO existe pasta global, elas são do template; um teste exige as 4 legais em todo template) entram em TODO site do template, preenchidas com `{{site.*}}`/`{{empresa.*}}`/`{{rel}}`; o site substitui (mesmo `caminho`) ou desliga (`paginasPadrao`). Textos legais estão como MODELO PROVISÓRIO até o jurídico do Revenda Mais mandar o oficial. Aviso de cookies e formulários por WhatsApp ficam no core (`core/ui/ui-site.js`), carregado por todas as páginas de todos os templates.
   - **Páginas livres dos designers** (HTML normal, sem JSON): `sites-config/<dominio>/web/paginas/` (só aquele site) e `templates/<nome>/paginas-extras/` (todos os sites do template). Lógica em `core/paginas-livres.js`. Prioridade de mesmo caminho: pasta do site (`web/paginas/`) > `paginas-extras/` do template > `paginas-padrao/` do template. Editar `paginas-extras` ou `paginas-padrao` NÃO refaz páginas de carro (ficam fora do hash do template). O designer não pode precisar mexer no core: tudo que ele fizer de comum (links "/x", título, imagens na pasta) o build resolve.
   - O web designer mexe só nos templates e nas pastas de páginas.
3. **Motor versionado, com rollout:** `core/motor/rascunho` é o único lugar onde se edita. `congelar vN` copia o rascunho para `core/motor/vN`, que passa a ser imutável. `aplicar vN --sites a,b` ou `--todos` roda os testes antes. Existem `reverter` e `historico`. O site fixa a versão em `"motor": "v3"`. Versões: v1 (base), v2 (ordenação destaque, carroceria), v3 (vários valores por filtro, ano exato, valor do link sem carro = nenhum carro). Site novo nasce com a última congelada.
4. **Filtros configuráveis por site:** estado, cidade, loja, marca, modelo, carroceria, ano (exato no v3; `tipo: "minimo"` = a partir de), preço, km, câmbio, combustível e cor. Estado, cidade e loja funcionam em cascata, e marca filtra modelo. Dá para mudar rótulos, opções e ordem, e há `restricoes` (precoMin, precoMax, anoMin, marcas, estados, cidades).
5. **Busca com tolerância a erro de digitação:** só tenta aproximar quando não há resultado exato. Palavras com 4 letras ou mais e não numéricas aceitam 1 erro (2 erros se tiver 7 letras ou mais). Ignora acento e maiúsculas, aceita pedaço de palavra e exige todas as palavras digitadas.
6. **Fotos no AWS S3:** `carros/<id>/<n>-<400|800|1600>.webp`, via `fotosBase`. Se a foto falhar, aparece um placeholder. O carro pode mandar `fotos` como número (já estão no armazenamento) ou como lista de URLs (`core/fotos.js` baixa e converte em segundo plano; o build conta só as fotos prontas, então o carro entra sem foto e a página dele é refeita quando elas ficam prontas). `node core/cli.js fotos [sites]` processa na mão.
7. **Links:** rotas da listagem `/multipla/revenda-estado-cod/pr/marca/audi|bmw?ord=menor` (estado da busca; ver Rotas acima), `/carros/<Marca>/<Modelo>/<Versao>/<Marca>-<Modelo>-<Versao>-<ano>-<Cidade>-<Estado>-<id>.html` (página estática por carro, com preview de WhatsApp; regra ÚNICA em `core/ui/link-carro.js`, usada no build, no navegador e nos testes) e `?v=carlos` (roteia o WhatsApp para o vendedor). Link de carro que muda (dados do estoque mudaram) vira redirecionamento para o novo por 180 dias (`retencaoRedirecionamentoDias`); o estado guarda `links`, `vendidos {data, link}` e `redirecionados` por site.
8. **Origem dos carros:** vêm de outro sistema (Revenda Mais). Ele terá UMA API que gera o JSON de carros de um estoque, e o Wellington chama quando achar melhor (gatilho manual, não é webhook obrigatório).

## Multi-tenant e Kubernetes (decisão do Wellington: escalar para 2500+ sites, EKS na AWS, vários inquilinos)
- **Inquilinos:** `inquilinos/<id>/inquilino.json` (nome, templates liberados, `rascunhos.padrao`) + `inquilinos/<id>/config/` (fotos, infra, publicacao, robots.txt, site-modelo). Site diz `"inquilino"` no site.json; sem ele = `padrao` (usa `config/` global). `core/inquilinos.js` resolve config do inquilino → global. Os 2 sites atuais (lojateste.com.br, primeseminovos.exemplo.com.br) são `revenda-mais` (rascunho `site{n}.carro57.com.br`).
- **Tokens por inquilino** (`api/clientes.js`): `"*"` = todos os sites DO inquilino; só `TOKEN_ATUALIZAR` (admin) atravessa. Domínio único na plataforma.
- **Escala:** `PAPEL=api|trabalhador|tudo` (api/servidor.js). Fila em arquivos no volume compartilhado (`api/fila.js`: pedidos, marcas por site, lotes); `api/trabalhador.js` reserva um site por vez (trava `fila-<canal>-<site>`), N pods em paralelo; canal `fotos` separado. Travas por site em `core/trava.js` (`.estado/travas/`, renovadas durante o trabalho, expiram em 5 min). Pendências de publicação por site (`core/pendentes.js`, reserva atômica). "Todos" = lote com um pedido por site.
- **Remover site:** `DELETE /v1/sites/<d>?confirmar=<d>` (core: `Ops.removerSite` → `Sites.arquivarArquivos`): arquivos para `.estado/removidos/<d>-<data>/` (recuperável), saída apagada, fotos apagadas (`Fotos.apagarFotosDoSite`), tokens atualizados, infra `remover`. O `autocentral.exemplo.com.br` foi removido assim em 2026-11-08 (os exemplos de páginas livres dele ficaram no git).
- **Templates do inquilino:** `inquilinos/<id>/templates/<nome>/` (no EFS, sem deploy) valem só para ele e substituem o da imagem de mesmo nome (`Inq.dirTemplate`). Travas renovadas durante o trabalho (`renovarMinhas` no laço do build), expiram em 5 min. Índice de pedidos por site/cliente.
- **Scripts de infra:** `ferramentas/infra/{criar,promover,renomear,remover}.sh` (CloudFront SaaS Manager + S3; `SIMULAR=1`), chamados pelo `infra.json` do inquilino com os IDs dele.
- **Infra:** `infra/docker/Dockerfile` (código na imagem; dados em /dados = EFS; `SITE_CARROS_TEMPLATES`/`SITE_CARROS_PAGINAS_PADRAO`), `infra/k8s/` (kustomize: EFS RWX, api + HPA, trabalhador + KEDA pela métrica `site_carros_fila_pedidos`, ALB, IRSA), `infra/cloudfront/roteador.js` (função de borda: index.html, barra final, `//`). `/v1/pronto` e `/metrics` para o Kubernetes. Nada aplicado numa conta AWS ainda.

## Pastas (decisão do Wellington, 2026-11-08)
- `sites-config/<dominio>/` = a FONTE de cada site (site.json, estoque.json, web/ (index.json, multipla.json, paginas/), componentes/, assets/), gravada pela API. Era `sites/`.
- `sites-public/<dominio>/` = a SAÍDA gerada pelo build (o que vai para o ar). Era `dist/`. **`sites-config` é a base de tudo que é gerado** (decisão do Wellington): pasta em sites-public sem site em sites-config é sobra; o build avisa e `node core/cli.js limpar-public [--aplicar]` apaga (`sobrasNaSaida` no build). O nome mora em `C.PUBLICO` (core/caminhos.js); funções recebem `pasta = C.PUBLICO`.
- As rotas da API continuam `/v1/sites/...` (endereço público da API, não é pasta).
- `core/sitemap.js`: `gerarSitemap(dominio)` reconstrói o sitemap.xml a partir do estado do build (páginas + carros no ar); o build usa `montarSitemap` ao reconstruir o site; `node core/cli.js sitemap [dominios]`.

## Componentes (decisão do Wellington, 2026-11-08)
- `componentes/<nome>/` (raiz, ao lado de `templates/`): UMA pasta, usada por todo template e toda página (não há componente por template). Hoje: `filtro`, `estoque` e `filtros-ativos` ("chips": etiqueta por filtro aplicado com X, botão "Limpar busca"; some sem filtro; `mostrar: false` tira) — os 4 templates usam os três no `multipla.html` (filtros-ativos logo acima do estoque). A lógica de todos fica na `core/ui/ui-lista.js` (peças opcionais: `#filtros-ativos`, caixas de marcar...).
- `componente.json` (opções com padrão, tipo, valores, `css` = variável CSS só do componente, `scripts` que ele precisa), `<nome>.html` (`{{op.*}}`, `{{{componente.estilo}}}`), `<nome>.css`/`.js` opcionais. `core/componentes.js` (mesclar/validar/renderizar/expandir).
- Uso: template `{{componente estoque colunas=280 titulo="{{listagem.h1}}"}}`; página `{ "tipo": "componente", "nome": "estoque", "opcoes": {...} }`; site inteiro `sites-config/<dominio>/componentes/<nome>.json` (decisão do Wellington: tudo do site é configurado em sites-config; o site.json recusa `"componentes"`; `ferramentas/mover-paginas.js` migra; API `GET/PUT/DELETE /v1/sites/<d>/componentes/<nome>`; `Sites.componentesDoSite`). Camadas: componente < template < site < página (bloco, ou `"componentes"` do `web/multipla.json` para os componentes do multipla.html). Filtro: opção `checkbox` (lista de campos que viram caixas de marcar, várias escolhas; motor v3) — na lojateste: estado, cidade, marca, modelo, carroceria (no `web/multipla.json`). Opção/valor inválido = erro claro (build e API 422). O build injeta css no `<head>` e `scripts` no `<body>` sem repetir; id do motor repetido na página = erro. Componente "estoque" em página ganha os primeiros cards no HTML (comCards). `node core/cli.js componentes` lista as opções. `core/ui/ui-lista.js` tolera peças ausentes (só #grade e #tpl-card obrigatórios).

## Como a atualização funciona (já implementado e testado)
- `node core/cli.js atualizar [dominios] [--publicar] [--forcar] [--completo]` busca em `config/fontes.json` (`{dominio: url | {url, headers}}`, aceita `${VAR}` de ambiente, timeout de 30 s).
- **Validação:** ids únicos, `loja` existente em `site.json` (obrigatória se o site tem mais de uma loja), marca/modelo/versão/cor/câmbio/combustível preenchidos, ano de 1950 até o ano atual + 2, preço > 0, km ≥ 0, fotos de 0 a 60. Qualquer erro → nada é gravado, e o estoque antigo continua valendo.
- **Trava de queda:** se o estoque cair mais de 50% (a partir de 10 carros), recusa. `--forcar` libera.
- Estoque igual ao anterior → nada acontece. O anterior é guardado em `.estado/estoques-anteriores/`.
- Só o site daquele estoque é refeito, e nele só as páginas dos carros que mudaram, mais o `estoque.json` da saída.
- **Carro que saiu:** a página vira "Este veículo não está mais disponível" (noindex) por `retencaoVendidosDias` (padrão 30, por site) e depois é apagada. Os links antigos dele apontam para essa página.
- Trocar motor ou filtros não refaz páginas. Trocar template, tema ou textos refaz as páginas do site.
- **Publicação:** `config/publicacao.json` = `{paralelo, comandoSite}`, com os placeholders `{site} {pasta} {lista} {removidos} {completo}`. Só limpa a pendência dos sites publicados com sucesso.
- Há trava de execução por site (`.estado/travas/`): sites diferentes em paralelo, o mesmo site nunca em dois ao mesmo tempo.
- **API agnóstica** (`api/`, contrato em docs/api.md): qualquer sistema cria/atualiza sites e manda estoque (1 ou N sites por chamada, inteiro ou carro avulso) com o token dele (`node api/cli.js cliente criar <nome> --sites a,b|*`). Criar site e refazer todos exigem `*`. Valida na hora (422), devolve número de pedido (`?esperar=N` responde com o resultado), junta rajadas (`ATRASO_MS`, 3000 ms) num build por site, e a fila fica em disco. Aceita até 100 MB no PUT do estoque.
- css/js saem com `?v=<hash do conteúdo>` (cache longo na CDN). Os do template entram no hash das páginas; os do core (`motor/`) não, então `core/ui` precisa continuar funcionando com HTML antigo.
- `problemasProducao(site)` no build: `url` sem https ou `fotosBase` em localhost/http → o build avisa e a publicação recusa o site.

## Medições (site de 1000 carros)
- `estoque.json` da saída (os carros que o motor lê; era `carros.json`, o build apaga o nome antigo; o feed `estoque.xml` saiu da plataforma por decisão do Wellington em 2026-11-08): 186 KB (15 KB com gzip). Com `"formatoEstoque": "compacto"` no site.json (`core/ui/formato-estoque.js`: dicionário + colunas; o mesmo arquivo compacta no build e desempacota no navegador/Node para a lista de sempre, então o motor e a busca não mudam): lojateste com 1500 carros 326 KB → 80 KB (gzip 33 → 24 KB). Motor + CSS + JS: ~25 KB (~10 KB com gzip). Página de carro: 4 KB. Pasta do site: 12 MB (1000 páginas).
- Chrome simulando celular (4G rápido, CPU 4x mais lenta): primeira tela 0,6 s, lista pronta 1,2 s, ~263 KB baixados, CLS 0.
- Em 3G lento (CPU 6x): primeira tela 0,8 s, lista pronta 1,8 s.
- Busca respondeu em ~140 ms.
- SEO: a `/multipla` já sai com os primeiros cards no HTML (montados pelo build com o `tpl-card` do template). Sitemap com `<lastmod>` real (dia em que a página mudou, guardado em `.estado`). O build gera `sitemap.xml`, `robots.txt` e JSON-LD (`Car` + `Offer`) quando o site tem `url`. As páginas de carro têm title, description, canonical e og:image.
- A compressão (gzip/brotli) precisa estar ligada no servidor/CDN.

## Regras ao mexer no código
- **Arquitetura de pastas é prioridade do Wellington:** core isolado em `core/`; cada site em `sites-config/<dominio>/` com subpastas; cada template inteiro dentro de `templates/<nome>/` (nada solto na raiz de `templates/`). Caminho novo → adicionar em `core/caminhos.js`.
- Nunca editar versões congeladas do motor (`core/motor/v1`, ...). Só `core/motor/rascunho`.
- Rodar `npm test` antes de entregar mudanças (296 testes, ~1 min com o Chrome; `npm run test:rapido` pula o Chrome). Bug corrigido → teste de regressão junto. O GitHub Actions roda os testes a cada push.
- `VERSAO_HTML` em `core/build.js`: aumentar SÓ quando mudar o HTML/JSON gerado pelo build (refaz as páginas de todos os sites). O `tests/snapshot-html.test.js` cobra; depois de aumentar, `npm run test:snapshot`.
- Versões congeladas do motor têm `sha256` em `versao.json` (o `congelar` grava); `tests/motor.test.js` falha se alguém editar uma.
- Os testes usam `SITE_CARROS_RAIZ` (pasta de dados temporária) e `construir({ hoje })` / `SITE_CARROS_HOJE` (data simulada para retenção).
- Build incremental: depois de mudar o `core/build.js`, rodar `node core/build.js` duas vezes. A segunda deve dizer "sem mudanças".
- Nos templates, referenciar arquivos sempre com `{{rel}}` (`{{rel}}css/style.css`, `{{rel}}motor/engine.js`). Imagens do `tema` com caminho relativo (`assets/logo.png`) já chegam com o prefixo certo em `{{tema.logo}}`.
- O template mini-renderer usa `{{x}}` (escapa), `{{{x}}}` (HTML cru, só gerado pelo build), `{{#x}}…{{/x}}` e `{{^x}}…{{/x}}`. Os cards ficam em `<script type="text/html" id="tpl-card">` com tokens `[[campo]]`.
- Tema por variáveis CSS: `--cor --fundo --texto --raio --fonte --colunas`.
- Ids da listagem: `grade` e `tpl-card` obrigatórios; opcionais `q, filtros-dinamicos, ord, contagem, mais, limpar, copiar, filtros-ativos` (a `ui-lista` tolera peça ausente; id repetido na página = erro no build).
- O motor é criado com `Motor.criar({dados:'estoque.json', config:'config.json', carregar})`.
